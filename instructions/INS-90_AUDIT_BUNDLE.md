# INS-90 — Ручная подготовка контекста для ИИ: context_bundle.py и AUDIT_BUNDLE.md

Тип: инструкция по процессу  
Статус: действует (Д-26, Д-27)  
Источник: порядок работы с ИИ, режимы — `instructions/README.md` §2

## 1. Назначение

Модель ИИ работает только с тем контекстом, который ей дали. Чтобы контекст
был одинаковым от сессии к сессии и не тратил токены на обход репозитория,
заказчик готовит его **вручную одним файлом** в локальном клоне и
прикладывает к сообщению. Инструментов два:

| | `tools/context_bundle.py` | `tools/make_audit_bundle.py` |
|---|---|---|
| Что собирает | «пол» чтения + файлы по ключам и путям задачи | снимок всего репозитория: список файлов и все текстовые файлы |
| Объём (на CP-22) | ~30 КБ (только пол) … ~110 КБ | ~705 КБ полный; ~165–300 КБ с профилями (§3.3) |
| Когда | задача по конкретным CP/Д/SPEC/INS — основной способ | review, аудит, широкие задачи, когда неизвестно, что понадобится |
| Требует | Python 3, рабочее дерево (git не обязателен) | Python 3 и git-клон (`git rev-parse`, `git ls-files`) |
| Выходной файл | `CONTEXT_BUNDLE.md` (stdout, имя по соглашению) | `AUDIT_BUNDLE.md` |

Оба файла — производные: не заменяют репозиторий и не коммитятся (в
`.gitignore`). Первоисточник — Git-репозиторий на base sha, указанном в
заголовке bundle.

Применение по режимам (`instructions/README.md` §2): в режиме B (AI Chat +
GitHub) bundle — стартовый контекст, недостающее модель дочитывает по
Д-12/Д-15; в режиме C (без GitHub) bundle — единственный источник. В
режиме A (Super Agent) агент собирает bundle сам в песочнице (Д-20).

## 2. context_bundle.py — контекст по ключам

### 2.1. Команда

```text
python tools/context_bundle.py --sha <base-sha> <ключ|путь> [...] > CONTEXT_BUNDLE.md
```

Пример: `python tools/context_bundle.py --sha $(git rev-parse HEAD) CP-20 Д-24 > CONTEXT_BUNDLE.md`.
`--sha` только подписывает заголовок bundle (`# base: …`); файлы читаются из
рабочего дерева — перед сборкой дерево должно быть на этом коммите и без
незакоммиченных правок.

### 2.2. Аргументы

| Вид | Формат | Что попадает в bundle |
|---|---|---|
| Ключ | `Д-##`, `CP-##`, `OQ-##`, `X-##`, `SPEC-##`, `CAT-##`, `INS-##`; регистр латиницы не важен (`cp-20` = `CP-20`) | **все** файлы, где встречается текст ключа (не более 300 файлов на ключ) |
| Путь | путь от корня репозитория, расширение `.md`, `.json`, `.py`, `.txt` | указанный файл |

Порядок в bundle: пол → пути → файлы по ключам; повторы убираются. Пол
(всегда первым): `README.md`, `specs/DECISIONS.md`, `specs/CODE_PLAN.md`,
`specs/CANCELLED.md`, `reports/checks.md`.

### 2.3. Как работает поиск по ключу — важно для выбора ключей

Поиск — по **подстроке**, без учёта границы числа:

- `Д-2` найдёт и `Д-20` … `Д-29` (на 71df0e6 — 18 файлов, ~124 КБ);
  пишите номер полностью, как в реестре: `Д-02`, `CP-05`, `SPEC-10`.
- Ключ, упомянутый в одном месте (в журнале, примере имени файла), тянет
  этот файл целиком.
- Файлы, где ключ не упомянут (часто — код), по ключу не попадут: добавляйте
  их путём.

### 2.4. Как выбрать ключи под задачу

1. Пункт плана задачи: `CP-##`.
2. Его основание (колонка «Основание» в CODE_PLAN): `Д-##`.
3. Затрагиваемые спецификации и инструкции: `SPEC-##`, `INS-##`.
4. Код и данные, где ключи не упомянуты: пути (`egm/…`, `specs/…_input.json`).
5. Проверьте состав по заголовку `# files:` и строкам `===== FILE:`; лишнее
   убирается более точным ключом, недостающее — путём.

Замеры на 71df0e6:

| Аргументы | Файлов | Объём |
|---|---|---|
| `README.md` (только пол) | 5 | ~30 КБ |
| `CP-20 Д-24` | 10 | ~38 КБ |
| `SPEC-10 INS-10 specs/ptk_input.json` | 14 | ~107 КБ |

### 2.5. Пределы и коды выхода

- Содержимое файла обрезается после 20 000 символов с пометкой
  `[...обрезано: N > 20000 символов...]` (на 71df0e6 — `egm/ptk.py`). Полный
  файл модель дочитывает по Д-15 (режим B) или заказчик прикладывает его
  отдельно (режим C).
- Код выхода: `0` — ok; `2` — неверный аргумент (bundle не выводится);
  `3` — ключ не найден ни в одном файле (bundle выводится, предупреждение в
  stderr). Несуществующий путь — только предупреждение в stderr, код 0:
  проверяйте stderr.
- Одинаковые base и аргументы дают байт-в-байт одинаковый bundle (Д-20).

## 3. make_audit_bundle.py — снимок AUDIT_BUNDLE.md

### 3.1. Команда

В корне локального git-клона, на нужном коммите:

```text
python tools/make_audit_bundle.py [--<профиль> ...] [--exclude ПРАВИЛО ...] [--out ФАЙЛ] [--list]
```

Без ключей — **максимально полный** снимок (исключается только базовый
`SKIP_FILES`), результат — `AUDIT_BUNDLE.md` в корне клона. `--list` выводит
профили и их правила, снимок не строится.

### 3.2. Состав

1. Заголовок `# AUDIT BUNDLE HarmonicV2`, `HEAD: <sha>` (`git rev-parse HEAD`)
   и строка `Profiles: …`, если заданы ключи исключения.
2. `## Git tree` — полный список файлов (`git ls-files`); исключённые файлы
   в нём остаются — модель видит, что файл есть, но его содержимого нет.
3. Список пропусков: каждое правило с обоснованием и, если правило — маска,
   перечень совпавших файлов (`-> N files: …`).
4. Содержимое текстовых файлов (`.md .py .json .toml .yaml .yml .txt .cfg
   .ini .j2 .jinja .jinja2 .csv .tsv .svg`), кроме исключённых; файлы
   больше 300 000 байт — пометкой «Skipped: file is too large».

Снимок отражает только текущее состояние: истории коммитов в нём нет.

### 3.3. Профили исключения (Д-27)

Исключение задаётся **правилом в синтаксисе `.gitignore`**, а не именем
файла. Базовые правила (`SKIP_FILES`) действуют всегда; профиль — ключ
запуска, добавляющий свой набор правил; ключи комбинируются.

| Ключ | Правила | Что убирает | Объём (на CP-22) |
|---|---|---|---|
| — (без ключей) | `docs/HG-Series-Catalog_opt.pdf` (base) | ничего сверх базового | ~705 КБ, 40 файлов |
| `--reports` | `docs/`, `specs/catalog_*.json` | каталоги производителей и производные БД каталога | ~300 КБ, 36 |
| `--ins` | `instructions/INS-10*`, `instructions/INS-20*` | инструкции к code-first спецификациям | ~690 КБ, 38 |
| `--data` | `specs/catalog_*.json`, `specs/ptk_configs.json` | производные данные прогона (дублируют SPEC и отчёты) | ~325 КБ, 37 |
| `--tools` | `tools/` | служебные утилиты | ~675 КБ, 37 |
| `--workflow` | `HarmonicV2-workflow.md` | референсная копия workflow (Д-25) | ~690 КБ, 39 |
| `--reports --ins` | все четыре правила | — | ~280 КБ, 34 |
| `--min` | все профили | только код, spec-first, журналы, отчёты, INS-00/90 | ~165 КБ, 29 |
| `--exclude ПРАВИЛО` | своё правило (повторяемый) | разовое исключение или `!путь` — вернуть файл | — |

Синтаксис правил (как в `.gitignore`, путь от корня репозитория):

- `docs/` — папка целиком; `*.pdf` (без `/` внутри) — имя на любой глубине;
- `specs/catalog_*.json`, `/README.md` (с `/`) — путь от корня;
- `*`, `?`, `[abc]` — в пределах сегмента пути; `**` — любое число сегментов;
- `!правило` — вернуть файл, исключённый раньше: `--min --exclude
  '!specs/catalog_hiwin_hg.json'`. Отличие от git: `!` возвращает файл и из
  исключённой папки.

Порядок применения: базовые → профили (в порядке объявления в `PROFILES`) →
`--exclude`; для файла действует последнее совпавшее правило. Неверное
правило — код выхода 2, неизвестный ключ — 2 (argparse).

Новый профиль добавляется в словарь `PROFILES` скрипта (имя ключа →
назначение и правила с обоснованием) и в таблицу этого пункта — в том же
патче.

### 3.4. Использование

1. Выберите профиль под задачу: review кода — `--reports` или `--min`;
   review документации — `--data --tools`; полный аудит — без ключей.
2. Приложите `AUDIT_BUNDLE.md` к первому сообщению; укажите задачу и что
   base sha — из заголовка. Если модели нужен исключённый файл — он виден в
   `## Git tree`: дошлите его отдельно или bundle по пути (§2).
3. Результаты review — в локальной папке `review_reports/` до отработки,
   затем удаляются; в git папка не хранится (Д-28).
4. Если модель упирается в лимит контекста даже с `--min` — переходите на
   bundle по ключам (§2).

## 4. Общие правила

1. Bundle собирается от закоммиченного состояния; base sha в заголовке =
   база патча, который вернёт модель (`# base: <sha>, CP-##`).
2. Новый коммит — новый bundle: старый не переиспользуется.
3. Патч от модели проверяется как обычно: `python tools/fix_diff.py p.diff`
   → `git apply --check` (главный `README.md`).
