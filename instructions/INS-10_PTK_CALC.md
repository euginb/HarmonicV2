Связанные решения: Д-08, Д-11, Д-16, Д-19, Д-31, Д-33, Д-35, Д-37, Д-38, Д-40…Д-43, Д-45,

Код: `egm/ptk.py` (подбор, ID, пределы), `egm/ptk_profile.py` (профиль, траектория (6) Янгулова),
`egm/ptk_force.py` (силы, Герц, момент, сепаратор), `egm/ptk_parts.py` (сепаратор, эксцентрик,

## 1. Что это и для чего

Функционал ПТК подбирает и проверяет исполнения одноступенчатого волнового редуктора
с промежуточными телами качения: для каждого u из диапазона, каждого тела качения,
каждого типа генератора и каждого крепления венца считается геометрия, профиль венца,
допускаемый выходной момент M и проверка габарита D. Результат — таблица SPEC-10, где
каждое исполнение имеет ID (Д-80). Затем выбранное исполнение прорабатывается: вал,
соединение эксцентрик–вал, балансировка под имеющиеся свёрла, опоры выхода. По выбранному
строится комплект чертежей — это уже **INS-30**.

Моментом `M` управляют пять пределов, и с CP-94…CP-96 к контакту и подшипнику добавились
сепаратор и обод: у сепаратора две расчётные схемы (Д-122), у обода — овализация и натяг на
кольцо подшипника (CP-96). Что именно упёрлось — в колонке «M (огр.)» и поле `M_by`.

Состав функционала: код — `egm/`; конфигурация — ручные YAML-файлы в `specs/`
(описание каждого параметра — комментарием рядом с ним, Д-79); инструкции — этот файл
и INS-30. Результаты прогона (SPEC-10/SPEC-11, `ptk_configs.yaml`, `ptk_designs.yaml`)
машина пишет сама — руками их не править (code-first).

## 2. Правила и flow

| Этап | Команда | Вход | Выход |
|---|---|---|---|
| 1. Расчёт | `python main.py calc --publish` | `specs/ptk_input.yaml`, `specs/vendor_prices.yaml` | `specs/SPEC-10_PTK_CALC.md`, `specs/ptk_configs.yaml` |
| — выбор | **человек**: по SPEC-10 выбрать исполнение (ID) | SPEC-10 | исполнение для шага 2 |
| 2. Проработка | `python main.py design --publish` | **опубликованный** `specs/ptk_configs.yaml` (выход шага 1), `specs/ptk_design_input.yaml` | `specs/SPEC-11_PTK_DESIGN.md`, `specs/ptk_designs.yaml` |
| 3. Чертежи | `python -m egm.cad --spec specs/cad_set.yaml` | `specs/cad_set.yaml` + `ptk_configs.yaml` + `ptk_designs.yaml` | `out/cad/**.svg|.step` |

Связь шагов явная (Д-79): вход шага 2 — опубликованный результат шага 1
`specs/ptk_configs.yaml`. Шаг 2 гоняется отдельно, не пересчитывая шаг 1: прогнали шаг 1,
выбрали исполнение, вписали проработку в `designs[]`, прогнали шаг 2 — сколько угодно раз.
`python main.py` без аргументов — прежний полный прогон: проверки ПО, шаг 1, шаг 2 по его
же свежим исполнениям, проверка номенклатуры, каталог (INS-20).

Почему у шага 2 «вход из будущего»: `designs[].id` ссылается на результат шага 1, хотя
файл заполняется до его прогона — это нормально, порядок такой: шаг 1 → выбор → шаг 2.
Чтобы проработка не терялась при смене хэша шага 1 (правка параметров меняет ID),
`id` пишут **префиксом без хэша** (Д-51, пример — в `ptk_design_input.yaml`); уточнение
нескольких исполнений под одним префиксом — полями `bearing` / `gen`.

Порядок изменения результатов — code-first: правите ручной конфиг (`specs/*.yaml`) →
прогон → смотрите `out/reports/checks.md` («все пройдены» = код выхода 0) → переносите
`--publish` → коммит. Значения и их смысл — в комментариях конфигов (первоисточник, Д-79);
этот файл — про логику и следствия.

## 3. Шаг 1 — «Расчёт» (`python main.py calc`)

### Вход

`specs/ptk_input.yaml` — `limits` (геометрия, материалы, диапазон), набор креплений
`ring_mounts`, режим `mount_mode`, таблица `fasteners`; `specs/vendor_prices.yaml` —
тела качения `rollers`, подшипники генератора `bearings`, цены `items`.
`pins` — штифты ГОСТ 24296 (Ø, стандартные длины); цена — items P<d>x<l> (Д-74)

Значения и «как влияет» — комментариями в самих файлах; ниже — только то, что нужно
для чтения результата.

### Что происходит

Для каждой тройки (u, тело, генератор) строится одноступенчатый редуктор; расчёт идёт
от центра наружу (обозначения — колонки SPEC-10):

```
z = u + 1,  n = u                          Д-31, Д-38: венец неподвижен, выход — сепаратор
aω    = a_k · Dш  (или a_w тела)           эксцентриситет генератора
RΣ min — наибольшее из условий             подрез, сепаратор, вал; колонка R_by (Д-38)
Dг    = D подшипника (bearing, Д-40) | Ø эксцентрика (eccentric, Д-42)
RΣ    = (Dг + Dш)/2                        окружность центров тел генератора
DВ    = 2(RΣ + aω) + Dш                    диаметр впадин венца
Dверш = 2(RΣ − aω) + Dш                    диаметр вершин
Dотв  = DВ + 2c     вверх до d_bc_step     окружность центров отверстий (Д-35)
D     = Dотв + 2c   вверх до d_out_step    наружный диаметр, ≤ d_out_max (Д-43)
c     = max(wall_min + d_clear/2, dk/2 + head_margin)
M     = min(M_H, M_B, M крепл./safety,
            M сеп., M обода)               Д-41, Д-116, CP-96; в скобках — ограничитель
```

c — расстояние от впадин до оси отверстия и от оси до наружной кромки; зависит только
от болта: чем крупнее болт, тем больше D при тех же телах. Какие строки попадают в
таблицу при нескольких креплениях — `mount_mode` (справочник §6.2). Пар «тело +
генератор», исключённых по технологии, касается §6.5 (Т1–Т4).

#### Пределы шага 1 и расчёт сепаратора (CP-94, CP-98, CP-95b, CP-96)

`M` — наименьший из пределов, каждый считается при одном и том же M пакета:

| Предел | Что ограничивает | Поле результата |
|---|---|---|
| `M_H` | контакт Герца: тело/генератор, тело/венец; у шарика — точечный, у ролика — линейный | `M_H`, `M_by_body` |
| `M_B` | статическая грузоподъёмность подшипника генератора (C0/P0) | `M_B` |
| `M крепл.` | трение стыка венца: `t_hold/safety` (штифты не учитываются) | `t_hold` |
| `M сеп.` | сепаратор .02: изгиб или контакт окна (ниже) | `M_sep`, `sep_chk`, `sep_why` |
| `M обода` | генератор `rim`: овализация обода .18 и σθ от натяга (CP-96) | `rim.M_ov`, `rim.dfl` |

Сепаратор считается по **двум схемам, берётся меньшая загрузка** (Д-122):

1. **рама Виренделя** — перемычки между окнами и пояса между рядами. Узлы рамы (ширина перемычки)
   считаются жёсткими, поэтому момент пояса уменьшается в `w/s` раз, где `w` — окно,
   `s = 2πR_Σ/n`: пояс гнётся только на пролёте окна, а не на всём шаге;
2. **сплошная полоса** — участок стенки шириной `b_c`, не перекрытый окнами ни одного ряда; он
   работает как консоль от выходного торца, пояса при этом не нагружены. Когда фазы окон
   перекрывают весь шаг (K20, n = 63), полосы нет и схема вырождается.

Загрузку ставят три механизма: изгиб (`[σ] = sep_sigma_m1/(sep_K·sep_S)`), срез пояса (`0.58·[σ]`)
и контакт тела со стороной окна (`[σ_H]`); `sep_why` в SPEC-10 называет механизм, элемент
(`перемычка` / `пояс j–j+1` / `торец` / `полоса` / `контакт`) и числа.

Важное следствие для чтения результатов: высота пояса по умолчанию равна зазору ряда
(`row_gap − sep_gap`), а не проектной величине. При узком подшипнике (61814, B = 10 мм при теле
16 мм) пояс выходит 0.95 мм и режет `M_sep` в разы, при широком (NU213-ECJ, B = 23 мм) — 7.95 мм.
То есть прочность сепаратора задаёт ширина B подобранного подшипника, а не расчёт. Отсюда `hb`
(добавка к шагу ряда) и `fill` (пояс до `t_max`) в обратной постановке.

### Выход

`specs/ptk_configs.yaml` — все исполнения машиночитаемо (вход шага 2 и INS-30);
`specs/SPEC-10_PTK_CALC.md` — та же таблица с расшифровкой. Оба — code-first.

### Как читать SPEC-10

Сначала «Статус». «нет» — причина в разделе «Нереализуемые конфигурации» (и в списке
ошибок в конце); коды Т# — §6.5; исключённые (Т1) — отдельным списком. «Dш max» — какое
тело поместилось бы при данном u. «M» — допускаемый выходной момент, в скобках — что его
ограничивает: «контакт» — Герц (M_H), «подшипник» — C0 подшипника генератора (M_B),
«крепление» — M крепл./safety, «сепаратор» — M_sep (механизм — `sep_why`, загрузка — `sep_chk`),
«обод» — овализация обода .18 (генератор `rim`).

Типовые правки (значения — в `ptk_input.yaml` / `vendor_prices.yaml`):

| Нужно | Что менять |
|---|---|
| проверить болт M5 вместо M4 | запись `"M5x8P2"` в `ring_mounts`, первой — чтобы стала основной |
| 12 отверстий вместо 8 | запись с `"n": 12` в `ring_mounts` |
| видеть все крепления, а не первое прошедшее | `mount_mode: all` |
| M ограничивает «крепление» | больше болтов или крупнее болт; `mu`, `safety` — по данным испытаний |
| M ограничивает «подшипник» | подшипник с большим C0 в `bearings` или тело крупнее |
| M ограничивает «сепаратор» по поясу | `row_gap` (квадратично, растёт и B), `limits.band_h_list` и `sep_band_t` (линейно, без роста D), тело короче |
| M ограничивает «сепаратор» по контакту окна | `limits.sep_sigma_H` (M ∝ `sep_sigma_H`² для ролика) — OQ-44: материал и упрочнение окна |
| M ограничивает «обод» (генератор `rim`) | `limits.rim_*`: толщина обода, натяг, `rim_k_ov` (OQ-48) |
| нужно ровно M, а не «сколько вышло» | `limits.u_calc → u → M_req` — обратная постановка, ниже |
| глубже волна, больше α max | больше `limits.a_k` (растёт RΣ по подрезу и D) |
| считать только с подшипником | `limits.gen_types: [bearing]` |
| добавить ролик Ø3×5 | запись в `vendor_prices.yaml` → `rollers` и `items` |
| таблица только для u = 30…60 | `limits.u_calc: {30: {}, 40: {}, 50: {}, 60: {}}` |
| два целевых момента для одного u | два ключа под этим u: `40: {600: {}, 900: {r_step: 0.5}}` |
| считать u только с двумя креплениями | `10: {ALL: {mounts: [M6x24P2, M5x12P2]}, 1500: {}}` |
| у всех u только ролики Ø8×16 и генератор с ободом | `ALL: {ALL: {rollers: [R_D8x16], gen_types: [rim]}}` |

## 4. Шаг 2 — «Проработка» (`python main.py design`)

### Вход

**Опубликованный результат шага 1** — `specs/ptk_configs.yaml` (связь шагов, §2) —
ID шага 1 не меняются; и `specs/ptk_design_input.yaml` — проработки `designs[]`:
имя (`name`), уточнение выбора (`bearing`, `gen`), вал (`shaft.d`, `bore`, `link`,
допускаемые), балансировка (`balance.drills` — Ø только из имеющихся свёрл), конструктив
(`layout`, Д-55) и опоры (`supports`). Значения и «как влияет» — комментариями в файле.
Порядок работы и причина «входа из будущего» — §2.

### Что считает

```
T_вх = M/(u·eta),   T_э = ecc_share·T_вх      M — допускаемый выходной момент SPEC-10
d_t  = d − t1 (шпонка),   β = bore/d_t
τ    = 16·T_вх/(π·d_t³·(1 − β⁴)) ≤ [τ]         d_req — Ø, при котором τ = [τ]
σ_см = 2·T_э/(d·(h − t1)·l_p) ≤ [σ см]        l_p = t − b, t — толщина эксцентрика
стенка у паза и напротив эксцентриситета (Dэ/2 − aω − d/2) ≥ ecc_wall_min
```

Шпонка — первая строка `keys.table` (specs/shafts.yaml, Д-109) с d ≤ `d_max` (призматическая исп. A, DIN 6885 /
ГОСТ 23360; сверить со справочником). Балансировка — как на шаге 1 (Д-36, Д-46), но
диаметры только из `balance.drills`. Масса пакета: эксцентрики, подшипники, вал длиной
B пакета; тела не учитываются. J вх — на входном валу (подшипники — кольца, обегающие
ось на aω, оценка сверху), J вых = J вх·u². Вал, шпонка и балансировка шага 2
переопределяют предварительные оценки шага 1 (Д-48, Д-53).

### Выход

`specs/ptk_designs.yaml` — проработки машиночитаемо (вход INS-30, в том числе для
`--design`); `specs/SPEC-11_PTK_DESIGN.md` — таблицы проработок, конструктива и оснастки.

### Как читать SPEC-11

«Статус» «нет» — причина в списке ошибок SPEC-11 (например, «вал Ø8: τ = 43.7 > [τ] = 25 МПа —
нужен d ≥ … мм»). «T вх / T э» — момент вала и доля одного эксцентрика. «Остаток» —
дисбаланс после отверстий, г·мм: «−» — перекомпенсация; больше 5 % U — предупреждение.
Детали проработки — таблица `<ID>.03<вар>-<name>` с углом паза и рядами.

Типовые правки:

| Нужно | Что менять |
|---|---|
| вал не проходит по τ | `shaft.d` ≥ d_req из текста ошибки (шпонка сменится по `keys.table` в specs/shafts.yaml) |
| τ близко к [τ] | следующий Ø вала новой записью `designs[]`: запас нужен при росте M (крепление, OQ-08) |
| полый вал под кабели | `shaft.bore`; проверить τ и `shaft.wall_min` |
| большой остаток балансировки | расширить `balance.drills` или `balance.n_max` |
| сравнить варианты вала | несколько записей с одним `id` и разными `name` |
| проработка потерялась после смены хэша | `id` — префиксом без хэша + `bearing` / `gen` (Д-51) |

## 6. Справочник

### 6.1 Обозначения

u — передаточное число; z — число впадин венца, z = u + 1 (Д-31); n — число тел в ряду;
aω — эксцентриситет генератора; RΣ — окружность центров тел; DВ / Dверш — впадины /
вершины венца; Dотв — окружность центров отверстий; D — наружный диаметр венца;
s — сдвиг сверловки ряда. Полный словарь — instructions/README.md §5.

### 6.2 Крепления венца: mount_mode и приоритет (Д-16, Д-33)

`ring_mounts` — словарь «имя → крепление»; каждая тройка (u, тело, генератор) считается
со всеми записями в порядке словаря. Режим `mount_mode`: `first_ok` (по умолчанию) —
в таблицу попадает первое прошедшее все проверки крепление (если ни одно — первое по
списку, с его ошибками); `all` — все, по строке на каждое. Порядок записей — приоритет:
первым основное (крупнее болт, больше M крепл.), за ним запасные для тесных случаев.
Имя (`M4x8P2`) — только метка: в ID не входит, состав отверстий входит (`8M4P2`).
Без штифтов (`pins: 0`) угловую фазу ряда держать нечем — только для проверки.

Шаг (хорда) = Dотв·sin(180°/n) ≥ max(dk + web_min, d_clear + wall_min);
M крепл. = n·F_M·mu·Dотв/2 — момент, передаваемый трением стыка (штифты не учитываются).
Одни и те же отверстия крепят редуктор в машине и базируют венец на оснастке станков
(ЭЭС, фрезерование); штифты H7 задают угловое положение.

### 6.3 Профиль венца (Д-38)

Вывод формул — SPEC-10 (текст генерируют `egm/ptk_profile.py`, `egm/ptk_force.py`).
Следствия для выбора параметров:

1. Профиль — эквидистанта траектории центра тела (6) Янгулова на Dш/2; глубина волны
   DВ − Dверш = 4aω — задаётся `a_k` и не зависит от u.
2. Угол передачи α max ≈ arctg √(2aω/Dш): при `a_k` = 0.2 около 32°. Меньший угол —
   больше радиальная сила на тело при том же M.
3. При больших u RΣ ограничивает подрез (`r_tip_min`): кривизна траектории на вершине
   растёт как aω·z², RΣ и D растут почти пропорционально u — u = 80, 100 выходят
   за `d_out_max`.
4. При малых u RΣ задают сепаратор (`sep_web_min`), вал или подшипник генератора;
   колонка «RΣ задан» показывает, какое условие сработало.

### 6.4 Фазировка рядов и сдвиг сверловки (Д-19)

Ряд k — копия ряда 1, повёрнутая на φk (эксцентрик генератора). Отверстия пакета
сквозные, в корпусе они на одних и тех же углах — поворот переносится на сверловку:

```
p = 360/z                 шаг впадин
N                         порядок симметрии сверловки (болты + штифты)
g = 360 / НОК(z, N)       шаг, по модулю которого сдвиги неразличимы
s_k = (−φk) mod g         поворот сверловки ряда k от впадины 0, град
s_k·π·Dотв/360            то же по дуге, мм (ptk_configs.yaml → s_arc_mm)
cage_k = ((−s_k·z − φk)/n) mod (360/n)   поворот окон ряда k в сепараторе (Д-46)
```

Венцы с одинаковым s — одна деталь. Буквы вариантов — `.01A`, `.01B`… — группы равного
s по порядку рядов: первая группа — A, следующая новая — B; ряды варианта —
`ptk_configs.yaml → parts[].rows` (таблица «Варианты деталей» — INS-30 §5). Все 4 венца
одинаковы, если z кратно 4 или N кратно 4. Примеры для 8 болтов:

| Штифты | N | Венцов при z = 20 | при z = 63 |
|---|---|---|---|
| 0 | 8 | 1 | 1 |
| 2 (напротив) | 2 | 1 | 2 |
| 4 (через 90°) | 4 | 1 | 1 |
| 1 или 3 | 1 | 1 | 4 |

Несимметричные штифты исключают неверную установку венца, но увеличивают число
вариантов и управляющих программ. Допущение: фаза — угол поворота эксцентрика ряда;
если фаза задаётся иначе (общий эксцентрик, поворот профиля на долю шага), формула
другая — сообщить исполнителю.

### 6.7 Покупные позиции (`vendor_prices.yaml`)

`rollers` — тела качения: ключ — обозначение (в ID и в `items`); `type` — `roller` |
`ball`; `d` = Dш, `l` — длина ролика (у шарика = Ø), мм; необязательные `a_w`,
`wall_min` переопределяют `limits` для этого тела. `bearings` — подшипники генератора
(Д-40): тела катятся по наружному кольцу, внутреннее сидит на эксцентрике; берётся
наименьший D ≥ 2·RΣ min − Dш с d ≥ `shaft_d_min` + 2(aω + `ecc_wall_min`); нет
подходящего — ошибка «нет подшипника генератора». Шаг ряда — max(l тела, B подшипника) + `hb` (обычно 0); ширина пакета
B = `rows`·шаг + (`rows` + 1)·`row_gap`. C, C0 серии 618 сверить с каталогом поставщика (OQ-09).

## Обратная постановка: таблица `u_calc` (CP-95, CP-99, Д-121, Д-123)

Прямая постановка задаёт `u` и минимизирует габарит — `M` получается следствием, и первым
ограничителем часто оказывается крепление (K20: 1740.7/1.5 = 1160.5 Н·м). Обратная постановка
задаёт требуемый момент и ищет наименьший габарит, в котором он реализуем.

**Вход — таблица `limits.u_calc`.** Ключ — u, значение — таблица вариантов расчёта этого u:
ключ варианта — целевой момент `M_req` (Н·м, > 0), значение — параметры варианта. Пустая таблица
`{}` у u — прямая постановка (M — следствие габарита), таблица с ключами — обратная; несколько
ключей у одного u дают несколько решений по этому u (по строке на вариант). Состав ключей u задаёт
таблицу SPEC-10 и границы одноступенчатого диапазона: первый и последний u — это `u_min…u_max`
(Д-119). Ключи `limits.u_list` и `limits.M_req` упразднены — при их наличии `load_config` падает с
указанием на `u_calc` (CP-99, Д-123).

**Слои (CP-101, Д-124).** Параметры складываются из трёх слоёв, следующий перекрывает
предыдущий (список заменяется целиком, а не дополняется):

```
u_calc.ALL.ALL            для всех u и всех вариантов
u_calc[u].ALL             для всех вариантов этого u (и для прямой постановки этого u)
u_calc[u][M_req]          для одного варианта
```

`u_calc.ALL` задаёт только параметры — состав u по-прежнему определяют ключи `u_calc`, то есть
`u_list` и границы `u_min…u_max`. `u_calc[u]` без вариантов (только `ALL` или пусто) — прямая
постановка этого u с унаследованными параметрами.

**Параметры слоя и варианта** (все необязательны):

| Ключ | Что задаёт |
|---|---|
| `r_step` | шаг подъёма R_Σ, мм (по умолчанию `limits.r_step`) |
| `r_up_max` | наибольший подъём R_Σ, мм (`limits.r_up_max`) |
| `band_h_list` | высоты пояса `hb`, мм (`limits.band_h_list`) |
| `mounts` | перечень креплений из `ring_mounts`, по которым считать этот u/вариант |
| `rollers` | перечень тел качения из `vendor_prices.yaml → rollers` |
| `gen_types` | типы генератора: `bearing`, `rim`, `eccentric` |

Перечень — список имён. Пустой список `[]` или отсутствие ключа — **без ограничения** (все), поэтому
`ALL.ALL: {mounts: [], rollers: [], gen_types: []}` ничего не меняет и служит напоминанием, где
задавать ограничения. Имя не из `ring_mounts`/`rollers` — `ValueError`: это опечатка, а не «нет
такого варианта»; пустой результат ограничения — тоже ошибка, чтобы u не выпал из таблицы молча.
`materials` зарезервирован и пока не принимается.

Перечни меняют состав строк SPEC-10, но не ID: в хэш они не входят (`GEOM_REV` = 6).

**Решение (`ptk.solve`).** Для тройки (u, тело, генератор) перебираются крепление `ring_mounts`,
подъём R_Σ (`dR`) и пояс сепаратора (CP-95b). `dR = 0, r_step, 2·r_step, …` до `r_up_max` или до
`D > d_out_max`; у `eccentric` и `rim` это `D_г = D_г min + 2·dR`, у `bearing` — подшипник с
`D ≥ 2(R_Σ min + dR) − D_ш`. Пояс перебирается по `limits.band_h_list` (по умолчанию 0, 2, 4, 6,
8 мм), на каждой высоте два варианта: без утолщения и `fill` — пояс до `t_max`. Шаг ряда при этом
max(l, B) + `hb`, поэтому `hb` растит B пакета (бывает, и D), а `fill` не меняет ни D, ни B —
только массу.

Порядок отбора: пояс перебирается только пока ограничивает сепаратор. Если упёрлись контакт,
подшипник, крепление, обод или габарит, пояс не поможет — перебор сразу идёт к следующему `dR`.
Целевая функция (D, B, −M): первое `dR`, где хоть один вариант пояса проходит, даёт минимальный
D, а на нём берётся наименьший `hb` — то есть минимальный B. Масса не сравнивается: на шаге 1 её
нет (Д-48).

Время прогона растёт как крепления × (`r_up_max/r_step`) × 2·`len(band_h_list)`: на прогоне
2026-11-19 — около 1.5 мин против 4 с без поясов. Если долго, сократите `band_h_list`
(например `[0, 4, 8]`).

Крепление в этом режиме — не «первое из списка», а подбираемое по моменту: если предел крепления
ниже `M_req`, перебор уходит на крепление мощнее или на больший `D_отв`, а не отбраковывает тройку.
`mount_mode: first_ok | all` в режиме `M_req` не действует — на каждую тройку выходит одна строка.

**Если `M_req` не достигнут.** В таблицу попадает реализуемая строка с наибольшим M (при
равенстве — с меньшими D и B), статус «нет», а в ошибке перечислены все потолки сразу: контакт
`M_H`, тело/окно `M_win`, крепление `t_hold/safety`, подшипник `M_B`, плюс границы перебора
(dR, hb, список креплений). В разделе SPEC-10 «Решение под M_req» по этому u печатается «нет
решения». Пример (u = 10, R_D8x16, `bearing`, прогон 2026-11-19): «наибольший M 646.4 (сепаратор);
потолки — контакт M_H 1333.5, тело/окно M_win 646.4, крепление 1340.5, подшипник 1254.2 Н·м».
Читается так: до 646 Н·м упирается контакт тела со стороной окна, а не изгиб пояса; поднять
потолок можно `sep_sigma_H` (OQ-44) или более длинным окном, а к 1500 Н·м следующим упрётся
`M_H`.

**Что меняется в ID (Д-80).** `M_req`, `r_step`, `r_up_max`, `band_h_list` в хэш не входят. `dR` входит только при
`dR > 0` и только у `eccentric`/`rim` (у `bearing` R_Σ задаёт подшипник, и он уже в хэше). Поэтому
ID прямой постановки сохраняются, `GEOM_REV` не повышается (Д-120). При смене крепления меняется
префикс ID (например `22M6P2` → `12M5P2`), при `dR > 0`, `hb > 0` или `fill` — хэш; привязки
`ptk_design_input.yaml` по префиксу в этом случае нужно перепроверить (`ptk_design.select`).
`fill` дополнительно даёт предупреждение «пояс до t_max … — CAD пояса нет» (OQ-46).

**Выход.** Колонка «M_req, Н·м» в таблице исполнений («—» — прямая постановка) и раздел «Решение
под M_req»: по каждому варианту (u, M_req) лучший вариант (ID, тело, генератор, dR, R_Σ, D, B,
M с ограничением) или «нет решения». В `ptk_configs.yaml` — поля `M_req`, `dR`; при `dR > 0` в `geom` появляется `dR`.

## 7. Материал сепаратора: `ptk_input.yaml` ↔ `materials.yaml`

Сепаратор .02 — единственная деталь шага 1, свойства материала которой задаются **не** ссылкой на
марку, а числами в `limits` файла `specs/ptk_input.yaml`. Шаг 1 не читает `specs/materials.yaml`
(его читают `egm/materials.py`, `egm/shafts.py`, `egm/ptk_layout.py` — шаг 2, валы, номенклатура),
поэтому марка, названная в справочнике, и марка, по которой посчитан `M_sep`, могут разойтись.
Сверять нужно руками:

| `ptk_input.yaml` | Сейчас | Что задаёт | `materials.yaml` |
|---|---|---|---|
| `sep_sigma_m1` | 509.0 МПа | σ₋₁ материала сепаратора → `[σ]` при изгибе | `40Х.sigma_m1` = 509 (улучшение, σв 980). У 38Х2МЮА — 392, после азотирования 608…617 |
| `sep_K` | 2.0 | концентратор в углах окон (OQ-44) | — |
| `sep_S` | 2.5 | запас многоцикловой усталости (OQ-44) | — |
| `sep_sigma_H` | 880.0 МПа | допускаемое σ_H контакта тело/сторона окна (OQ-44) | — (свойство пары, не марки) |
| `sep_k_edge` | 1.2 | ужесточение контакта у кромки стенки окна | — |
| `sep_band_t` | 0.0 | толщина пояса; 0 — равен стенке (OQ-46) | — |
| `sep_band_gap` | 0.2 мм | зазор утолщённого пояса до шайбы .05 | — |
| `sep_gap` | 0.05 мм | зазор тела в окне (геометрия, входит в `GEOM_LIMITS`) | — |
| `rho` | 7850 кг/м³ | масса добавки пояса `dm` | 38Х2МЮА `rho` 7.71 (7710), 40Х 7.82 |

**Как считается.** `[σ] = sep_sigma_m1 / (sep_K · sep_S)` — сейчас 509/5 = 101.8 МПа. От `[σ]`
линейно зависит `M_sep` по изгибу (перемычка, пояс, полоса); по контакту окна `M_sep` зависит от
`sep_sigma_H` как `[σ_H]^p`, где p = 2 для ролика и 3 для шарика (Герц). Что лимитирует —
`sep_why` и `sep_chk.by` («изгиб» / «контакт»).

**Сопоставление по маркам.** `materials.yaml` называет основной маркой .02 38Х2МЮА
(`use: "сепаратор .02 — основная марка (TECH-01)"`), а вход шага 1 считает по σ₋₁ 40Х. Переход на
38Х2МЮА в улучшенном состоянии: `sep_sigma_m1` 392 → `[σ]` 78.4 МПа, и `M_sep` по изгибу падает до
0.77 от текущего (u = 10, R_D8x16, `bearing`: было 646.4 — проверить по фактическому `sep_why`,
лимит там по контакту, поэтому значение не изменится). Азотирование даёт σ₋₁ 608…617 → `[σ]`
122…123 МПа (+20 %), но лимит по контакту окна этим не поднимается: он задаётся `sep_sigma_H`.
К 1500 Н·м при u = 10 нужен `sep_sigma_H` ≈ 1.5·[σ_H], то есть ≈1340 МПа (M ∝ `[σ_H]`²), а следом
упрётся `M_H` — OQ-44.

**Что править.** Марку и состояние сепаратора — через `sep_sigma_m1` (и `rho` для массы пояса) в
`specs/ptk_input.yaml`; значения брать из `materials.yaml` той марки, что стоит в
`products.yaml → parts.02.material`. `sep_sigma_m1`, `sep_K`, `sep_S`, `sep_sigma_H`, `sep_k_edge`,
`sep_band_t` в хэш ID не входят (их нет в `GEOM_LIMITS`): ID не меняются, но `M_sep`, статусы и
строки «нет решения» меняются — после правки обязателен прогон с `--publish`.
