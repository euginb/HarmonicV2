# INS-91B — Подготовка контекста локальным агентом (без AI Drive)

Тип: инструкция по процессу
Статус: действует (2026-10-30)
Источник: дополнение к `instructions/INS-91_CONTEXT_PREP.md` — режим для агента
с полным доступом к локальному репозиторию (без облачного AI Drive и зеркала)

## 1. Назначение

`INS-91` описывает работу **Super Agent** с зеркалом `/HarmonicV2-main.zip` из
AI Drive. У локального агента (GigaCode) нет AI Drive и зеркала, но есть полный
прямой доступ к репозиторию `C:\Users\eugin\PycharmProjects\HarmonicV2\`.

`INS-91B` — адаптированный порядок: агент читает файлы напрямую из рабочей
директории, использует `git` для сверки base sha и выдаёт результат тем же
каналом (CTX-блок + p.diff/upd.md), но без записи в AI Drive.

## 2. Режимы работы

| Режим | Пусковая фраза | Что делает агент |
|---|---|---|
| T — задача → код | `Контекст для задачи: <задача> (CP-##)` | собирает CTX-T (~200 КБ), §3.1 |
| R — ретроспектива → план | `Контекст для ретроспективы: <тема>` | собирает CTX-R (~400 КБ), §3.2 |
| Прямая работа с токеном | запрос с токеном GitHub | клон (или локальный репозиторий), правки, коммит, push (§8) |
| Проверка патча | `Проверь патч из чата` | верифицирует p.diff/upd.md через `tools/fix_diff.py` → `git apply --check` |

Если задача не привязана к CP — номер в имени пропускается.
Пример: «Контекст для задачи: каталог штифтов в vendor_prices».

### 3.6. Формат подачи файлов

По умолчанию агент **не включает** полные содержимые файлов в ответ — только
описания и ссылки. Для передачи контекста модели AI Chat (или для записи в
`patch/response/*.md`) используются два формата:

#### 3.6.1. Ручная подача (описания + ссылки)

Внутри ответа или файла `patch/response/*.md` агент пишет:

```
===== FILE: <путь> (строки 1–N) =====
```

Внутри — **сырой контент** без номеров строк, с маркером языка:

```python
"""docstring"""
import json

def foo():
    ...
```

**Важно:** номера строк — **только в заголовке**. Строки внутри — чистые.
Это критично: `tools/fix_diff.py` ищет hunk по содержимому, а не по номерам.

#### 3.6.2. Контекстный bundle через context_bundle.py

Инструмент `tools/context_bundle.py` автоматически собирает bundle по ключам:

```bash
python tools/context_bundle.py [--sha <base-sha>] <ключи...> > <output.md>
```

Пример:
```bash
python tools/context_bundle.py --sha HEAD Д-100 Д-101 CP-85 CP-86 CP-87 > patch/response/rev11.6-ctx.md
```

**Формат вывода** (INS-91 §4, §5):

```
# CONTEXT BUNDLE
# base: <sha>
# items: Д-100, Д-101, CP-85...
# files: N

===== FILE: README.md =====
<полное содержимое файла>
===== END FILE =====

===== FILE: specs/DECISIONS.md =====
<полное содержимое файла>
===== END FILE =====

...

# END BUNDLE
```

**Как работает:**
1. `context_bundle.py` сначала включает «пол» (FLOOR): `README.md`, `specs/DECISIONS.md`,
   `specs/CODE_PLAN.md`, `specs/CANCELLED.md`, `reports/checks.md`
2. Затем ищет файлы, содержащие переданные ключи (Д-##, CP-##, OQ-## и т.д.)
3. Для каждого найденного файла включает **полное содержимое** (до 20 000 символов)

**Ограничения:**
- `MAX_FILES = 300` — предел файлов от одного ключа
- `MAX_CHARS = 20 000` — предел символов одного файла
- Если файл больше — обрезается с пометкой `[...обрезано...]`
- На Windows может потребоваться `PYTHONUTF8=1 python ...` из-за кодировки stdout

**Применение:**
- Для AI Chat — приложить сгенерированный файл целиком
- Для локальной работы — читать из `patch/response/<ключ>.md`
- Для прямых правок (с токеном) — контекст не нужен

#### 3.6.3. Выбор формата

| Сценарий | Формат |
|---|---|
| Передача AI Chat (лимит токенов) | `context_bundle.py` + сжатие до ~200 КБ |
| Локальная проверка (агент читает сам) | Ручная подача §3.6.1 или bundle |
| Прямая работа с токеном | Не нужно |

### 3.7. Запись контекста в patch/response/*.md

#### 3.7.1. ctx_task.py — целевой контекст по ключам задачи

`tools/ctx_task.py` — улучшенная версия `context_bundle.py`, которая собирает контекст
не просто по ключам, а с учётом семантики задачи:

```bash
python tools/ctx_task.py [--sha SHA] CP-## ... > patch/response/ctx_<key>.md
```

**Отличие от context_bundle.py:**
1. Читает CODE_PLAN.md → извлекает файлы из столбца «Файлы» каждого CP
2. Добавляет **семантические файлы** по смыслу задачи:
   - Для CP-88 (layout, products): ptk_design_input.yaml, products.yaml, **stock.yaml** (КРИТИЧНО — порядок layout влияет на выбор заготовки из stock), ptk_layout.py
   - Для CP-89 (materials): materials.yaml, materials.py, config.py
3. Для .py файлов: если ключи есть в файле — включает строки с ключами ±3; иначе — скелеты
4. Для .yaml: целиком (структура важна)
5. Для .md: «пол» целиком; остальное — строки с ключами ±5
6. Порядок: пол → семантические файлы → CP-файлы

**Пример:**
```bash
python tools/ctx_task.py --sha HEAD CP-88 CP-89 > patch/response/rev11.7-ctx-CP88-89.md
```

**Результат:** 934 строки, 12 файлов (включая пол и Д-100).

## 4. CTX-T — задача (~200 КБ)

Структура CTX-T:

1. **Заголовок**: `# CTX-T HarmonicV2 — <описание задачи>`
   + строки: `base: <sha>`, `rev: <NN.N>`, `date: <дата>`, `keys: ...`
2. **«Пол»** — §2.1 (выборкой: малые файлы целиком, DECISIONS и CODE_PLAN —
   строки с ключами задачи + смежные, когда бюджет ограничен)
3. **Инструкции для модели** — дословный блок из `INS-91 §4` (§5 настоящей инструкции)
4. **Карта репозитория** — §3.2
5. **Затрагиваемые файлы** — §3.4, сырыми блоками
6. **Отсутствующее** — файлы, не вошедшие, с причиной

Приоритет сокращения: смежные фрагменты → `docs/` → производные JSON → карта.

## 5. CTX-R — ретроспектива (~400 КБ)

Структура CTX-R:

1. **Заголовок**: `# CTX-R HarmonicV2 — <тема>` + base / rev / date / keys
2. **«Пол»** (целиком, как в CTX-T) + `git log -n 20` (последние 20 коммитов)
3. **Инструкции для модели** — §5, дословно
4. **Импорт-граф** — по всему `egm/` и `tools/`
5. **Код ядра** — `main.py`, `egm/ptk*.py`, `egm/catalog.py`, `egm/config.py`,
   `egm/materials.py`, `egm/products.py`, `egm/naming.py`, `egm/calc_vptc.py` —
   дословно с номерами строк; остальное (`egm/cad/`, `tools/`) — скелеты
6. **specs/*.md и specs/*.yaml** — дословно; производные JSON — статистика
7. **Открытые положения** — OQ-* и X-## списком

Результат R-режима: план — новые/уточнённые CP-## с основаниями Д-## и
затрагиваемыми файлами; следующие шаги — задачи T-режима.

## 6. Инструкции для модели — дословный блок (копируется в CTX)

Ниже — точный блок, который включается в каждый CTX-файл:

    Результат работы — два файла, каждый отдельным код-блоком:
    1. p.diff — unified diff; первая строка: `# base: <sha>, CP-##` (sha — из
       строки «base» заголовка этого файла). Правила: пути a/… и b/…; строки
       контекста — полные и точно из этого файла; номера строк — ориентир,
       hunk ищется по содержимому (tools/fix_diff.py поправит синтаксис);
       новые файлы — заголовком diff --git, new file mode 100644,
       --- /dev/null, +++ b/<путь>; не-ASCII имена файлов — сырым UTF-8,
       без экранирования; markdown-обрамление вокруг diff не используется.
    2. upd.md — для строк таблиц и новых файлов. Директива Journal: путь в
       одинарных кавычках, после двоеточия — заголовок раздела с таблицей
       (как в файле); ниже — строки таблицы; ключ — значение первой ячейки:
       есть в таблице — строка заменяется целиком, нет — добавляется в
       конец. Директива NewFile: путь в кавычках; ниже — содержимое файла
       до следующей директивы или конца. Строка содержимого, начинающаяся
       с решётки и трёх дефисов, непредставима — такие строки правимого
       файла давайте через diff.
    3. Файл, нужный для задачи, но отсутствующий в контексте, называется
       явно: «Отсутствует: <путь>» — его досылают отдельно; по памяти не
       угадывать.
    4. Положение относительно исходного файла: CTX-файл несёт заголовки
       `===== FILE: <путь> (строки 1–N) =====` (диапазоны — в заголовках);
       правка Journal привязывается к заголовку раздела, а не к номеру
       строки.

### 7.3. Выдача контекста: patch/response/*.md

CTX-файл (полный или сжатый) записывается в `patch/response/<ключ>.md`:

## 8. Полная обработка ответа от модели (локальный агент)

Когда локальный агент выступает в роли **исполнителя** (а не подготовителя
контекста), модель возвращает результат работы в виде двух код-блоков:
`p.diff` и `upd.md`. Агент обязан **полностью распарсить ответ**, извлечь
блоки, применить к репозиторию, закоммитить и (при наличии токена) push.

### 8.1. Формат ответа модели

Модель должна вернуть **два отдельных код-блока** (порядок не важен, но
рекомендуется сначала `p.diff`, затем `upd.md`):

```
<любой текст>

```diff
# base: <7-40 hex sha>, CP-##
diff --git a/... b/...
...
```

<любой текст>

```
# --- Journal: 'specs/DECISIONS.md': ## Решение...
| Д-99 | ... |
| Д-100 | ... |
# --- NewFile: 'egm/new_module.py'
"""docstring"""
...
```
```

**Важные правила модели** (из INS-91_CONTEXT_PREP.md §4):

1. **p.diff** — unified diff **без** markdown-обрамления (без \`\`\`diff)
   внутри блока. Первая строка: `# base: <sha>, CP-##`.
   Номера строк — ориентир, hunk ищётся по содержимому.
2. **upd.md** — директивы `Journal` и `NewFile` (см. §8.2).
3. Файл, отсутствующий в контексте — модель явно пишет «Отсутствует: <путь>».

### 8.2. Парсинг ответа

Агент извлекает блоки из ответа модели по следующему алгоритму:

**Извлечение p.diff:**
1. Найти все блоки ````diff ... ```` или ```` ... ```` (трёх- или четырёх-
   тильды).
2. Первый блок, содержащий строку, начинающуюся с `# base:`, — это `p.diff`.
3. Извлечь содержимое между маркерами код-блока (без маркеров).
4. Если блок не найден — проверить, нет ли текста, начинающегося с
   `# base:` и содержащего `diff --git`.
5. Из первой строки извлечь `base_sha` и `CP-##` (или другой ключ задачи).

**Извлечение upd.md:**
1. Найти блок, содержащий директивы `# --- Journal:` или `# --- NewFile:`.
2. Если таких блоков несколько — объединить в один upd.md.
3. Если блок не найден — установить флаг `upd_empty = True`.

**Проверка целостности:**
- Если `p.diff` не найден — ошибка: «Модель не вернула p.diff».
- Если `upd.md` не найден — продолжить без него (блок может отсутствовать).
- Если оба блока в одном — допустимо.

### 8.3. Применение p.diff

**Шаг 1 — запись во временный файл:**
```
Записать извлечённый p.diff в patch/response/apply_<cp_key>_<timestamp>.diff
```

**Шаг 2 — нормализация через fix_diff.py:**
```
python tools/fix_diff.py patch/response/apply_*.diff --root .
```
Результат: `apply_*.diff.fixed.diff`

**Что делает fix_diff.py:**
- Нормализует кодировку (UTF-16/UTF-8-BOM → UTF-8, CRLF → LF)
- Удаляет markdown-обрамление (если модель всё же добавила)
- Декодирует C-квотинг путей (октальные \NNN в UTF-8)
- **Сверяет hunk'и с рабочим деревом** — ищет контекст по содержимому,
  а не по номерам строк
- Корректирует отступы добавляемых строк из файла
- Добавляет '\ No newline at end of file' при необходимости
- Сливает соседние hunk'и для сохранения контекста

**Шаг 3 — проверка:**
```
git apply --check patch/response/apply_*.diff.fixed.diff
```
- Если ошибка — распечатать сообщение, **НЕ коммитить**, запросить у
  пользователя уточнения.
- Если успех — перейти к шагу 4.

**Шаг 4 — применение:**
```
git apply patch/response/apply_*.diff.fixed.diff
```
- Если ошибка — распечатать, не коммитить.
- Если успех — файл изменён в рабочем дереве.

### 8.4. Применение upd.md

**Шаг 1 — запись во временный файл:**
```
Записать извлечённый upd.md в patch/response/apply_<cp_key>_upd.md
```

**Шаг 2 — применение через upd_apply.py:**
```
python tools/upd_apply.py patch/response/apply_*_upd.md --root .
```

**Что делает upd_apply.py:**
- Парсит директивы `Journal` и `NewFile`
- **Journal:** ищет раздел по заголовку таблицы, находит строку по ключу
  (первая ячейка), заменяет целиком или добавляет в конец
- **NewFile:** создаёт файл (и родительские каталоги) с содержимым блока
- Валидирует: число ячеек = шапке, ключ уникален, путь относительный
- Атомарность: ошибка в одном блоке не применяет другие блоки из файла

**Шаг 3 — проверка результата:**
- Если код выхода 0 — всё применено.
- Если код выхода 1 — распечатать ошибки, **НЕ коммитить**.

### 8.5. Коммит изменений

**Сбор информации:**
```
git status                          # какие файлы изменены
git diff HEAD                       # полный diff
git log -n 3                        # стиль последних коммитов
```

**Формат сообщения:**
```
[<имя-ветки>] CP-## <краткое описание изменений>
```

Примеры:
- `[rev-11.4] CP-46 Добавил расчёт канавки для сепаратора`
- `[rev-11.5] CP-50 Обновил DECISIONS.md и добавил vendor_prices`

**Создание коммита:**
```
git add <изменённые файлы>
git commit -m "[<имя-ветки>] CP-## <описание>"
```

**Важные правила:**
- Автор коммита — euginb (noreply-адрес)
- Формат `[<имя-ветки>]` обязателен (GIGACODE.md §Правила оформления коммитов)
- Если изменений несколько (p.diff + upd.md в разных файлах) — **один**
  коммит, а не два
- Если push запрещён (нет явной команды «пушь») — **НЕ пушить**

### 8.6. Push (только при явном запросе)

**Правило абсолютное** (GIGACODE.md):
- **НИКОГДА** не выполнять push без явной команды пользователя
- Даже при успешном коммите и прогоне `main.py`
- Исключение: пользователь сказал «пушь», «push», «отправь на сервер»
  или аналогичную прямую команду

**При наличии токена и явной команды:**
```
git push origin <имя-ветки>
```

**Сообщение пользователю:**
```
Коммит: <sha>
Push: success (или error с описанием)
```

### 8.7. Прогон main.py (после применения)

После успешного применения и коммита — прогнать `main.py`:
```
python main.py all
```

- Если код выхода 0 — отметка OK (Д-01)
- Если код выхода ≠ 0 — распечатать ошибки, **не закрывать CP-##**
- Прогон и отметка OK — **заказчиком** (Д-01), но агент может прогнать
  для предварительной проверки

### 8.8. Создание PR через `tools/create_pr.py`

После успешного коммита и прогона `main.py`, при явной команде пользователя
создать и запушить PR, затем выполнить мердж и создать новую ветку ревизии.

#### 8.8.1. Подготовка

1. Убедиться, что ветка с изменениями запушена на origin:
   ```
   git push origin <ветка>
   ```
2. Переменная окружения `GITHUB_TOKEN` или `GH_TOKEN` должна содержать
   токен с правами `repo` (или `public_repo` для публичных репозиториев).

#### 8.8.2. Создание PR

```bash
python tools/create_pr.py <head> <base> [options]
```

Параметры:
- `head` — имя ветки с изменениями (обязательно, должна быть на origin)
- `base` — базовая ветка для мерджа (обычно `main`)
- `-t, --title` — заголовок PR (по умолчанию: `[rev-NN.N] <описание>`)
- `-m, --message` — тело PR (Markdown, по умолчанию — краткое описание)
- `--dry-run` — вывести JSON запроса, не отправляя
- `--repo` — репозиторий в формате `owner/repo` (по умолчанию: `euginb/HarmonicV2`)

Примеры:
```bash
# Автозаголовок, авто-тело
python tools/create_pr.py rev11.8 main

# Кастомный заголовок
python tools/create_pr.py rev11.8 main -t "[rev-11.8] CP-90 Новые расчёты"

# Кастомное тело
python tools/create_pr.py rev11.8 main -t "Заголовок" -m "## Изменения\n- ... \n\n## Проверки\n- OK"

# Dry-run
python tools/create_pr.py rev11.8 main --dry-run
```

Результат — URL созданного PR в stdout.

#### 8.8.3. Мерж PR

Пользователь мержит PR вручную через GitHub UI или командой:
```bash
gh pr merge <PR-NUMBER> --squash --delete-branch
```

Или через API:
```bash
gh pr merge <PR-NUMBER>
```

После мерджа убедиться, что локальная ветка `main` обновлена:
```bash
git fetch origin && git checkout main && git pull origin main
```

#### 8.8.4. Создание новой ветки ревизии

После мерджа создать новую ветку для следующей итерации:
```bash
git checkout main
git pull origin main
git checkout -b rev<NN.N+1>
git push origin rev<NN.N+1>
```

Пример:
```bash
git checkout main
git pull origin main
git checkout -b rev11.9
git push origin rev11.9
```

#### 8.8.5. Полный сценарий

```
git push origin <ветка>
  ├─→ python tools/create_pr.py <ветка> main
  │     → PR URL в stdout
  │
  ├─→ (пользователь мержит PR через GitHub)
  │
  ├─→ git fetch origin && git checkout main && git pull origin main
  │
  ├─→ git checkout -b rev<новая>
  │
  └─→ git push origin rev<новая>
```

### 8.9. Интеллектуальная обработка ошибок (auto-fix retry)

Ошибки при применении патчей от ИИ — **ожидаемое явление**. Модель ошибается
в номерах строк, отступах, заголовках разделов. Не нужно сразу останавливаться
и запрашивать уточнения — агент должен **анализировать ошибку и пытаться
исправить автоматически**.

#### 8.9.1. Общая стратегия

| ШАГ | Действие |
|---|---|
| 1 | Зафиксировать ошибку — распечатать полный вывод |
| 2 | Определить тип ошибки (таблица ниже) |
| 3 | Применить автофикс (таблица ниже) |
| 4 | Повторить попытку |
| 5 | Если ошибка повторилась ≥ 2 раза — запросить у пользователя |

**Ограничение retry:** максимум **3 попытки** для p.diff и **2** для upd.md.
После исчерпания — остановка, запрос пользователя.

**Откат перед retry:** если `git apply` прошёл частично, откатить:
```
git checkout -- .           # откатить все незакоммиченные изменения
git clean -fd               # удалить неотслеживаемые файлы (остатки NewFile)
```

#### 8.9.2. Типы ошибок p.diff и автофиксы

| Тип ошибки | Сообщение fix_diff.py / git apply | Автофикс |
|---|---|---|
| **Номера строк неверны** | `hunk не найден`, `лучшее совпадение...совпало N из M` | fix_diff.py **сам** ищет hunk по содержимому по всему файлу (§2). Retry не нужен — если fix_diff написал предупреждение, а не ОШИБКУ, применяем. |
| **Hunk в неправильном порядке** | `order of hunks doesn't match file` | fix_diff.py **сам** сортирует hunk'и (§2). Не retry. |
| **Смежные hunk'и потеряли контекст** | `hunk без хвостового контекста` | fix_diff.py **сам** сливает соседние hunk'и (§2). Не retry. |
| **Контекст совпал только с точностью до пробелов** | `предупреждение: отступ взят из файла` | Не ошибка. Retry не нужен. |
| **Hunk уже применён** | `hunk уже применён — пропущен` | Не ошибка. Retry не нужен. |
| **Полное совпадение, но блок недоступен** | `полное совпадение найдено, но блок недоступен (лежит раньше курсора)` | **Retry с очисткой:** откатить изменения, прочитать актуальный файл заново, перекоммитить. |
| **Hunk перекрывается с уже найденным** | `перекрывается с уже найденным hunk'ом` | **Retry №1:** откатить, удалить перекрытый hunk из патча, retry. |
| **Нет совпадений вообще** | `лучшее совпадение: совпало 0 из N` | **Retry №1:** прочитать актуальный файл заново, пересобрать hunk. **Retry №2:** если не вышло — запросить пользователя. |
| **Обрезан хвост контекста** | `хвост первой/последней строки контекста в патче обрезан` | Не ошибка. Retry не нужен. |
| **Файл не найден в рабочем дереве** | `файл не найден в рабочем дереве` | **Retry №1:** проверить, не был ли файл переименован/удалён. Если переименован — найти новый путь. **Retry №2:** запросить пользователя. |
| **Файл помечен как новый, но существует** | `помечен как новый, но уже существует` | **Ошибка:** файл уже есть. Удалить директиву NewFile из патча, retry. |
| **Путь в diff не совпадает с файлом** | `файл не найден` | **Retry №1:** проверить, не был ли файл переименован. Если да — найти новый путь. |
| **CRLF/кодировка** | `unexpected end of file`, `invalid byte sequence` | Не ошибка — fix_diff.py сам конвертирует (§2). Retry не нужен. |

#### 8.9.3. Типы ошибок upd.md и автофиксы

| Тип ошибки | Сообщение upd_apply.py | Автофикс |
|---|---|---|
| **Раздел не найден** | `раздел '...' не найден` | **Retry №1:** прочитать файл, найти все заголовки с таблицами, сравнить с указанным разделом (регистронезависимо, убрать `##`, пробелы). Если раздел найден с другим написанием — исправить в патче. **Retry №2:** запросить пользователя. |
| **Нет таблицы в разделе** | `в указанном разделе нет таблицы` | Не ошибка — значит в файле изменилась структура. **Retry №1:** прочитать актуальный файл, найти нужную таблицу вручную. **Retry №2:** запросить пользователя. |
| **Неоднозначный ключ** | `ключ встречается N раз — неоднозначно` | **Ошибка:** ключ не уникален. Удалить строку из upd.md, retry. Если ключ действительно не уникален — запросить пользователя. |
| **Несоответствие числа ячеек** | `ячеек N, в шапке таблицы M` | **Ошибка:** модель неправильно отформатировала строку. Прочитать шапку таблицы, добавить/удалить ячейки до совпадения. **Retry №1:** исправить и повторить. **Retry №2:** запросить пользователя. |
| **Строка вне таблицы** | `строка вне таблицы в блоке Journal` | **Ошибка:** модель добавила обычный текст вместо строк таблицы. Удалить строки, retry. |
| **Путь абсолютный или с ..** | `путь должен быть относительным` | **Ошибка:** исправить путь на относительный от корня репозитория. Retry. |
| **Файл уже существует (NewFile)** | `файл уже существует (перезаписать — --overwrite-new)` | **Retry:** если файл действительно должен быть новым — применить с `--overwrite-new`. Если файл старый — перенести директиву в раздел Journal. **Retry №1:** перекомпоновать директивы. **Retry №2:** запросить пользователя. |
| **Раздел не тот** | `раздел не найден; разделы с таблицами: ...` | **Retry №1:** выбрать один из найденных разделов, исправив путь в патче. Retry. |

#### 8.9.4. Алгоритм auto-fix retry

```
для каждой ошибки:
    попытка = 0
    пока попытка < MAX_RETRY:
        попытка += 1

        1. Записать ошибку в лог: patch/response/auto_fix_log.txt
        2. Определить тип ошибки (таблицы §8.9.2/§8.9.3)
        3. Применить автофикс:
           • Если fix_diff выдал ПРЕДУПРЕЖДЕНИЕ, но не ОШИБКУ → применять
           • Если fix_diff выдал ОШИБКУ → попытаться исправить патч
        4. Повторить git apply --check
        5. Если success → выйти из цикла, применить патч
        6. Если ошибка → откатить (git checkout -- .)

    если попытка >= MAX_RETRY:
        Запросить пользователя:
        "Ошибка auto-fix №N: <тип ошибки>
         Попытки исчерпаны. Детали: <лог>
         Продолжить без этого блока / исправить вручную?"
```

#### 8.9.5. Лог auto-fix

Каждую попытку автофикса записывать в `patch/response/auto_fix_log.txt`:

```
--- Auto-fix attempt #N при YYYY-MM-DD HH:MM ---
Ошибка: <полное сообщение>
Тип: <тип ошибки>
Автофикс: <что сделано>
Результат: success / error: <сообщение>
---
```

При запросе пользователя — показывать полный лог.

#### 8.9.6. Edge-case: файл изменён после подготовки CTX

Если модель готовила контекст на old sha, а к моменту применения файл уже
изменился (другой коммит, pull) — hunk может не найтись.

**Действия:**
1. Проверить `git log --oneline -10` — не ушёл ли origin?
2. Если origin ушёл вперёд — `git fetch`, прочитать актуальные файлы
3. Перекомпоновать патч с актуальными файлами
4. Retry

**Если актуальный файл сильно изменился:**
- Запросить пользователя: «Файл <путь> изменился после подготовки контекста.
  Пересобрать CTX и патч или применить с ручными правками?»

#### 8.9.7. Резюме по ошибкам

| Ситуация | Действие |
|---|---|
| fix_diff → предупреждение (не ошибка) | Применять, не retry |
| fix_diff → ошибка "уже применён" | Пропустить, не retry |
| fix_diff → ошибка "порядок hunk" | Пропустить, не retry (fix_diff сам сортирует) |
| fix_diff → ошибка "не найден" | Retry №1: прочитать файл заново, перекомпоновать |
| upd_apply → ошибка "раздел не найден" | Retry №1: найти раздел по заголовку, исправить путь |
| upd_apply → ошибка "ключ неоднозначен" | Удалить строку, retry |
| upd_apply → ошибка "число ячеек" | Исправить строку, retry №1 |
| Оба инструмента → ошибка ≥ 3× | Запросить пользователя |
| Файл изменён после CTX | git fetch, перечитать, перекомпоновать |

#### 8.10. Диаграмма процесса (полная обработка)

```
Ответ модели
    │
    ├─→ Парсинг: извлечь p.diff
    │       │
    │       ├─→ Не найден → ОШИБКА
    │       │
    │       └─→ Найден → Записать во временный файл
    │
    ├─→ Парсинг: извлечь upd.md
    │       │
    │       ├─→ Не найден → upd_empty = True (допустимо)
    │       │
    │       └─→ Найден → Записать во временный файл
    │
    ├─→ fix_diff.py (нормализация p.diff)
    │       │
    │       └─→ git apply --check (проверка)
    │               │
    │               ├─→ Ошибка → §8.9 auto-fix retry (до 3×)
    │               │       │
    │               │       ├─→ Исправлено → git apply (применение)
    │               │       │
    │               │       └─→ Не исправлено → Запросить пользователя
    │               │
    │               └─→ OK → git apply (применение)
    │
    ├─→ upd_apply.py (если upd.md не пуст)
    │       │
    │       └─→ Проверка кода выхода
    │               │
    │               ├─→ Ошибка → §8.9 auto-fix retry (до 2×)
    │               │       │
    │               │       ├─→ Исправлено → OK
    │               │       │
    │               │       └─→ Не исправлено → Запросить пользователя
    │               │
    │               └─→ OK
    │
    ├─→ git status + diff
    │
    ├─→ git commit -m "[<ветка>] CP-## <описание>"
    │
    ├─→ main.py all (предварительная проверка)
    │
    └─→ Push (ТОЛЬКО по явной команде)
```

## 9. Отличия в ограничении бюджета

У локального агента лимиты контекста обычно выше, чем у AI Chat, но ограничены.
Приоритеты при сокращении CTX-T:

1. **Никогда не сокращать**: пол (§2.1), инструкции (§5), ключевые файлы задачи
2. **Первым под сокращение**: смежные модули (импорт-граф, не ядро задачи)
3. **Затем**: `docs/`, производные JSON (`catalog_*.json`, `ptk_configs.json`)
4. **Карта репозитория**: можно сократить до ключевых директорий

При R-режиме (бюджет ~400 КБ) сокращать минимум: ядро — всегда дословно,
спеки — дословно, остальное — скелеты.
