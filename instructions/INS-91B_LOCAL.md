# INS-91B — Подготовка контекста локальным агентом (без AI Drive)

Тип: инструкция по процессу
Статус: действует (2026-10-30)
Источник: дополнение к `instructions/INS-91_CONTEXT_PREP.md` — режим для агента
с полным доступом к локальному репозиторию (без облачного AI Drive и зеркала)

## 1. Назначение

`INS-91` описывает работу **Super Agent** с зеркалом `/HarmonicV2-main.zip` из
AI Drive. У локального агента (GigaCode) нет AI Drive и зеркала, но есть полный
прямой доступ к репозиторию `C:\Users\eugin\PycharmProjects\HarmonicV2\`.

`INS-91B` — адаптированный порядок: агент читает файлы напрямую из рабочей
директории, использует `git` для сверки base sha и выдаёт результат тем же
каналом (CTX-блок + p.diff/upd.md), но без записи в AI Drive.

## 2. Режимы работы

| Режим | Пусковая фраза | Что делает агент |
|---|---|---|
| T — задача → код | `Контекст для задачи: <задача> (CP-##)` | собирает CTX-T (~200 КБ), §3.1 |
| R — ретроспектива → план | `Контекст для ретроспективы: <тема>` | собирает CTX-R (~400 КБ), §3.2 |
| Прямая работа с токеном | запрос с токеном GitHub | клон (или локальный репозиторий), правки, коммит, push (§8) |
| Проверка патча | `Проверь патч из чата` | верифицирует p.diff/upd.md через `tools/fix_diff.py` → `git apply --check` |

Если задача не привязана к CP — номер в имени пропускается.
Пример: «Контекст для задачи: каталог штифтов в vendor_prices».

## 3. Порядок сбора контекста

Агент работает в рабочей директории — локальный клон репозитория.

### 3.1. Стартовый «пол» (обязательно, каждый раз)

Любая сессия начинается с одного и того же набора файлов:

1. `README.md` — целиком (структура, правила, реестр спецификаций)
2. `specs/DECISIONS.md` — целиком (или строки с ключами задачи + смежные, если бюджет ограничен)
3. `specs/CODE_PLAN.md` — целиком (или строки с ключами задачи + смежные)
4. `specs/CANCELLED.md` — целиком
5. `reports/checks.md` — целиком

Эти файлы — фундамент контекста. Они не зависят от задачи.

### 3.2. Определение ключей задачи

По запросу агента выделяются идентификаторы:

| Паттерн | Что означает | Где ищется |
|---|---|---|
| `Д-##` | Решение проекта | Задача, DECISIONS.md, архив |
| `OQ-##` | Открытый вопрос | Задача, DECISIONS.md |
| `X-##` | Отменённое положение | Задача, CANCELLED.md |
| `CP-##` | Пункт плана кода | Задача, CODE_PLAN.md |
| `SPEC-##` | Спецификация | Задача, specs/ |
| `CAT-##` | Каталог | Задача, CATALOGS.md |
| `INS-##` | Инструкция | Задача, instructions/ |
| `TECH-##` | Технология | Задача, docs/ |
| `rev-##` | Ревизия | Позирует в имени ветки / коммита |

### 3.3. Сборка карты репозитория

Агент строит карту, ранжируя файлы по объёмам и назначению:

```
===== REPO MAP =====
README.md          (~200 строк) — обзор, правила работы
specs/DECISIONS.md (~200 строк) — решения Д-##, открытые вопросы OQ-##
specs/CODE_PLAN.md (~100 строк) — план доработки CP-##
specs/SPEC-10_PTK_CALC.md (~200 строк) — спецификация ПТК
...
egm/ptk.py         (~620 строк) — калькулятор ПТК
egm/catalog.py     (~150 строк) — парсинг каталогов
...
```

Карта — раздел 4 в CTX-файле.

### 3.4. Сбор затрагиваемых файлов

По ключам задачи агент выбирает файлы:

1. **Решения Д-## / OQ-## / X-##** — соответствующие строки из DECISIONS.md / CANCELLED.md
2. **CP-##** — строки из CODE_PLAN.md → список файлов из столбца «Файлы»
3. **SPEC-##** — файл specs/SPEC-##.md
4. **INS-##** — файл instructions/INS-##.md
5. **Модули egm/** — через `import_graph` (или вручную по `from ... import`)
6. **Конфиги** — specs/*.yaml, configs/application.yaml

Правила подачи:

- **Дословно** — ядро, справочники, конфиги (импорты, сигнатуры, значения)
- **Скелет** — `egm/cad/`: сигнатуры и докстринги (через ast)
- **Фрагмент** — `egm/ptk*.py`: функция/класс/место вызова
- **Производные данные** — stats: ключи верхнего уровня, число записей, выборка 3–5 строк

### 3.5. Import-граф

Агент строит граф импортов по затронутым модулям (вручную или через
`tools/import_graph.py --roots egm main.py`):

```
main.py
  ├── egm.ptk
  │     ├── egm.ptk_force
  │     ├── egm.ptk_parts
  │     └── egm.ptk_profile
  ├── egm.catalog
  ├── egm.config
  ├── egm.naming
  ├── egm.products
  └── egm.cad.ptk_ring
```

Импортеры / imported-by — для выбора смежных модулей.

### 3.6. Формат подачи файлов

```
===== FILE: <путь> (строки 1–N) =====
```

Внутри — **сырой контент** без номеров строк, с маркером языка:

```python
"""docstring"""
import json

def foo():
    ...
```

Для YAML:

```yaml
key: value
```

Для markdown:

```markdown
# Заголовок
```

**Важно:** номера строк — **только в заголовке**. Строки внутри — чистые.
Это критично: `tools/fix_diff.py` ищет hunk по содержимому, а не по номерам.

## 4. CTX-T — задача (~200 КБ)

Структура CTX-T:

1. **Заголовок**: `# CTX-T HarmonicV2 — <описание задачи>`
   + строки: `base: <sha>`, `rev: <NN.N>`, `date: <дата>`, `keys: ...`
2. **«Пол»** — §2.1 (выборкой: малые файлы целиком, DECISIONS и CODE_PLAN —
   строки с ключами задачи + смежные, когда бюджет ограничен)
3. **Инструкции для модели** — дословный блок из `INS-91 §4` (§5 настоящей инструкции)
4. **Карта репозитория** — §3.2
5. **Затрагиваемые файлы** — §3.4, сырыми блоками
6. **Отсутствующее** — файлы, не вошедшие, с причиной

Приоритет сокращения: смежные фрагменты → `docs/` → производные JSON → карта.

## 5. CTX-R — ретроспектива (~400 КБ)

Структура CTX-R:

1. **Заголовок**: `# CTX-R HarmonicV2 — <тема>` + base / rev / date / keys
2. **«Пол»** (целиком, как в CTX-T) + `git log -n 20` (последние 20 коммитов)
3. **Инструкции для модели** — §5, дословно
4. **Импорт-граф** — по всему `egm/` и `tools/`
5. **Код ядра** — `main.py`, `egm/ptk*.py`, `egm/catalog.py`, `egm/config.py`,
   `egm/materials.py`, `egm/products.py`, `egm/naming.py`, `egm/calc_vptc.py` —
   дословно с номерами строк; остальное (`egm/cad/`, `tools/`) — скелеты
6. **specs/*.md и specs/*.yaml** — дословно; производные JSON — статистика
7. **Открытые положения** — OQ-* и X-## списком

Результат R-режима: план — новые/уточнённые CP-## с основаниями Д-## и
затрагиваемыми файлами; следующие шаги — задачи T-режима.

## 6. Инструкции для модели — дословный блок (копируется в CTX)

Ниже — точный блок, который включается в каждый CTX-файл:

    Результат работы — два файла, каждый отдельным код-блоком:
    1. p.diff — unified diff; первая строка: `# base: <sha>, CP-##` (sha — из
       строки «base» заголовка этого файла). Правила: пути a/… и b/…; строки
       контекста — полные и точно из этого файла; номера строк — ориентир,
       hunk ищется по содержимому (tools/fix_diff.py поправит синтаксис);
       новые файлы — заголовком diff --git, new file mode 100644,
       --- /dev/null, +++ b/<путь>; не-ASCII имена файлов — сырым UTF-8,
       без экранирования; markdown-обрамление вокруг diff не используется.
    2. upd.md — для строк таблиц и новых файлов. Директива Journal: путь в
       одинарных кавычках, после двоеточия — заголовок раздела с таблицей
       (как в файле); ниже — строки таблицы; ключ — значение первой ячейки:
       есть в таблице — строка заменяется целиком, нет — добавляется в
       конец. Директива NewFile: путь в кавычках; ниже — содержимое файла
       до следующей директивы или конца. Строка содержимого, начинающаяся
       с решётки и трёх дефисов, непредставима — такие строки правимого
       файла давайте через diff.
    3. Файл, нужный для задачи, но отсутствующий в контексте, называется
       явно: «Отсутствует: <путь>» — его досылают отдельно; по памяти не
       угадывать.
    4. Положение относительно исходного файла: CTX-файл несёт заголовки
       `===== FILE: <путь> (строки 1–N) =====` (диапазоны — в заголовках);
       правка Journal привязывается к заголовку раздела, а не к номеру
       строки.

## 7. Дифференциация от INS-91

| Аспект | INS-91 (AI Drive) | INS-91B (локально) |
|---|---|---|
| Репозиторий | зеркало `/HarmonicV2-main.zip` | локальный клон (рабочая директория) |
| base sha | из журнала синхронизаций | `git rev-parse HEAD` или `git rev-parse <ветка>` |
| Выдача патчей | `/HarmonicV2-patches/` в AI Drive | `upd.md` текстом в чате; при токене — push напрямую |
| CTX-файлы | `/HarmonicV2-ctx/` в AI Drive | текстом в чате (лимит токенов) или через токен |
| Синхронизация | «синхронизируй зеркало» | `git fetch` + проверка на обновлённую ветку |
| Зависимости | песочница (cadquery и др.) | локальная среда (как настроена) |

### 7.1. Сверка актуальности

Агент проверяет, что локальная ветка не отстала:

```bash
git fetch origin
git log --oneline origin/<ветка>..HEAD   # что есть локально, но нет на origin
git log --oneline HEAD..origin/<ветка>   # что есть на origin, но нет локально
```

Если origin ушёл вперёд — уведомить пользователя.

### 7.2. Работа с токеном

Если пользователь передал токен GitHub (§8 INS-91), агент работает с
репозиторием напрямую:

```
Репозиторий: https://github.com/euginb/HarmonicV2
Ветка работы: <ветка> (по умолчанию — ветка текущей ревизии, напр. rev11.4)
base: <tip sha ветки>
Права: токен пользователя — чтение, коммит и push напрямую;
инструкции §4 действуют; результат — коммит(ы) и push, sha — в ответе.
```

Коммиты — с префиксом `[<имя-ветки>]`, как в `GIGACODE.md` (§Правила оформления коммитов).

## 8. Отличия в ограничении бюджета

У локального агента лимиты контекста обычно выше, чем у AI Chat, но ограничены.
Приоритеты при сокращении CTX-T:

1. **Никогда не сокращать**: пол (§2.1), инструкции (§5), ключевые файлы задачи
2. **Первым под сокращение**: смежные модули (импорт-граф, не ядро задачи)
3. **Затем**: `docs/`, производные JSON (`catalog_*.json`, `ptk_configs.json`)
4. **Карта репозитория**: можно сократить до ключевых директорий

При R-режиме (бюджет ~400 КБ) сокращать минимум: ядро — всегда дословно,
спеки — дословно, остальное — скелеты.
