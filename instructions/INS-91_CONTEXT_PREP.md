# INS-91 — Подготовка контекста Super Agent'ом: CTX-T и CTX-R

Тип: инструкция по процессу  
Статус: действует (Д-78, rev 10.3)  
Источник: порядок работы с ИИ — `instructions/README.md` §2; заменяет ручную
сборку бандла для моделей без GitHub — INS-90 остаётся запасным путём

## 1. Назначение и роли

Модели категории AI Chat (без агентских функций и доступа к GitHub) видят
только приложенные файлы. Ручная сборка бандла по ключам (INS-90) не
масштабируется: основная масса бандла — код и производные данные, которые
нельзя ранжировать по важности ключами; урезанный снимок (`--min`) на
6c148baa — ~747 КБ, и неочевидно, что из него убирать.

Поэтому начиная с rev 10.3 контекст готовит **Super Agent в песочнице**: он
разворачивает зеркало `/HarmonicV2-main.zip` из AI Drive, анализирует задачу
против репозитория (реестры CP/Д/OQ, импорт-граф, пол из INS-00 §2.4) и
выдаёт один готовый файл. Заказчик только прикладывает его к модели AI
Chat. Локальный клон и запуск context_bundle.py / make_audit_bundle.py
заказчику не нужны (INS-90 — запасной путь, когда Super Agent недоступен).

Схема (оба режима):

1. Заказчик говорит Super Agent'у пусковую фразу (§2).
2. Super Agent собирает CTX-файл и кладёт его в `/HarmonicV2-ctx/` в AI
   Drive + прикладывает к ответу.
3. Заказчик прикладывает файл к модели AI Chat; модель работает только с ним.
4. Результат модели — `p.diff` + `upd.md` текстом в чате (правила — внутри
   CTX-файла, §4; повторять их в запросах не нужно).
5. Заказчик передаёт результат на проверку: «Проверь патч из чата» —
   Super Agent проверяет (`tools/fix_diff.py` → `git apply --check`;
   `tools/upd_apply.py` `--dry-run`) и кладёт в `/HarmonicV2-patches/`.
6. Заказчик применяет патч в локальном клоне, коммитит, пушит.
7. «Синхронизируй зеркало HarmonicV2» — обычная короткая фраза.

## 2. Пусковые фразы (весь входной сигнал)

| Режим | Фраза | Что делает агент |
|---|---|---|
| T — задача → код | `Контекст для задачи: <задача> (CP-##)` | собирает CTX-T (~200 КБ), §3.1 |
| R — ретроспектива → план | `Контекст для ретроспективы: <тема>` | собирает CTX-R (~400 КБ), §3.2 |
| Проверка | `Проверь патч из чата` | верифицирует p.diff/upd.md, кладёт в `/HarmonicV2-patches/` |

Пример: «Контекст для задачи: каталог штифтов в vendor_prices (CP-66)».
Если задача не привязана к CP — номер в имени опускается.
Ожидаемый результат T-режима — код: `p.diff` + `upd.md` (§4).

## 3. Состав CTX-файла

Файл один, UTF-8 без BOM, LF. Разделы в порядке ниже; строка `base` в
заголовке — база будущего патча (зеркало соответствует последнему push).

### 3.1. CTX-T — задача (~200 КБ)

1. Заголовок `# CTX-T HarmonicV2 — <задача>` и строки: `base: <sha>`,
   `rev: <NN.N>`, `date: <дата>`, `keys: CP-##, Д-##, OQ-## …` (реестры,
   по которым шёл отбор).
2. «Пол» (INS-00 §2.4): `README.md`, `specs/DECISIONS.md`,
   `specs/CODE_PLAN.md`, `specs/CANCELLED.md`, `reports/checks.md` —
   дословно.
3. Инструкции для модели — §4 настоящей инструкции, дословно.
4. Карта репозитория: файлы с объёмами и назначением; импорт-граф
   затрагиваемых модулей (`tools/import_graph.py`, §6).
5. Затрагиваемые задачей файлы — дословно, с номерами строк
   (`===== FILE: <путь> (строки 1–N) =====`, номер строки перед каждой
   строкой); смежные (importers / imported-by по графу) — только
   релевантные секции (функция, класс, место вызова).
6. Отсутствующее — файлы, не вошедшие в файл контекста, с причиной; модель
   называет их явно, они досылаются отдельно.

Приоритет сокращения до ~200 КБ: смежные фрагменты → `docs/` →
производные JSON (`catalog_*.json`, `ptk_configs.json`) → карта репозитория.

### 3.2. CTX-R — ретроспектива (~400 КБ)

1. Заголовок `# CTX-R HarmonicV2 — <тема>` и те же строки; плюс `scope:` —
   что включено.
2. «Пол» + журнал из `/HarmonicV2-workflow.md` (последние ~20 записей:
   патчи, синхронизации, отказы и их причины).
3. Инструкции для модели — §4.
4. Импорт-граф (текст + mermaid) по всему `egm/`, `tools/`.
5. Код: ядро (`main.py`, `egm/ptk*.py`, `egm/catalog.py`, `egm/config.py`,
   `egm/materials.py`, `egm/products.py`, `egm/naming.py`,
   `egm/calc_vptc.py`) — дословно с номерами строк; остальное (`egm/cad/`,
   `tools/freecad_*`) — скелеты: сигнатуры и докстринги (через ast).
6. `specs/*.md` и `specs/*.yaml` — дословно; производные данные
   (`specs/*.json`) — статистика: ключи верхнего уровня, число записей,
   выборка 3–5 строк; `docs/` — оглавление (заголовки); `reports/` —
   дословно (небольшие).
7. Открытые положения: OQ-* и X-* списком (`specs/DECISIONS.md`,
   `specs/CANCELLED.md`).

Результат R-режима: план — новые/уточнённые пункты CP-## с основаниями
Д-## и затрагиваемыми файлами; следующие шаги — сформулированные задачи
T-режима (по фразе на шаг).

## 4. Инструкции для модели — дословный текст в каждом CTX-файле

Ниже — точный блок, который копируется в CTX-файл (оба режима); при сборке
не меняется. Врезка в контекст снимает необходимость упоминать правила
выдачи в каждом запросе.

    Результат работы — два файла, каждый отдельным код-блоком:
    1. p.diff — unified diff; первая строка: `# base: <sha>, CP-##` (sha — из
       строки «base» заголовка этого файла). Правила: пути a/… и b/…; строки
       контекста — полные и точно из этого файла; номера строк — ориентир,
       hunk ищется по содержимому (tools/fix_diff.py поправит синтаксис);
       новые файлы — заголовком diff --git, new file mode 100644,
       --- /dev/null, +++ b/<путь>; не-ASCII имена файлов — сырым UTF-8,
       без экранирования; markdown-обрамление вокруг diff не используется.
    2. upd.md — для строк таблиц и новых файлов. Директива Journal: путь в
       одинарных кавычках, после двоеточия — заголовок раздела с таблицей
       (как в файле); ниже — строки таблицы; ключ — значение первой ячейки:
       есть в таблице — строка заменяется целиком, нет — добавляется в
       конец. Директива NewFile: путь в кавычках; ниже — содержимое файла
       до следующей директивы или конца. Строка содержимого, начинающаяся
       с решётки и трёх дефисов, непредставима — такие строки правимого
       файла давайте через diff.
    3. Файл, нужный для задачи, но отсутствующий в контексте, называется
       явно: «Отсутствует: <путь>» — его досылают отдельно; по памяти не
       угадывать.
    4. Положение относительно исходного файла: CTX-файл несёт номера строк
       файлов; правка Journal привязывается к заголовку раздела, а не к
       номеру строки.

## 5. Положение относительно исходного файла

Дифф и upd.md ссылаются на состояние файлов на base sha:

* файлы в CTX несут номера строк — ориентир для модели при составлении
  hunk'ов и правок;
* точность номеров не критична: `tools/fix_diff.py` ищет hunk по
  содержимому по всему файлу (номера строк могут врать), но base sha в
  заголовке патча должен совпадать с указанным в CTX: новый коммит — новый
  CTX (§7);
* правка Journal в upd.md позиционируется заголовком раздела таблицы, а не
  номером строки (INS-00 §2.5) — «переформатированная» таблица не мешает;
* NewFile позиционируется путём; существующий файл — ошибка применения.

## 6. Инструменты: импорт-граф

`tools/import_graph.py` (Д-78) — граф импортов, только stdlib (ast):

```text
python tools/import_graph.py [--mermaid] [--roots egm tools main.py] [--out FILE]
```

Вывод (текст): по каждому модулю — LOC, imports (внутренние), imported by;
точки входа (не импортирует никто); циклы импорта. `--mermaid` — диаграмма.
В CTX-T включается по затрагиваемым модулям, в CTX-R — по всему `egm/` и
`tools/` (§3.2). Новый модуль подхватывается автоматически по корням —
поддержки при добавлении файлов не требуется.

## 7. Хранение и срок жизни

CTX-файлы: `/HarmonicV2-ctx/` в AI Drive; имена `CTX-T-CP-##-<slug>.md` и
`CTX-R-<ГГГГ-ММ-ДД>-<slug>.md` (slug латиницей). Файл соответствует base
sha из заголовка: новый коммит — новый CTX, старый не переиспользуется
(как у бандла, INS-90 §4). Файлы не удаляются (история). Проверенные
патчи — `/HarmonicV2-patches/` (как обычно).
